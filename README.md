## How the website works

The pages are in [docs/](docs/): `index.md` in English, `index.de.md` in German, `releases.md` and `releases.de.md` with the notes of the latest releases of every project, `trust.md` and `trust.de.md` with the guarantees of every project, `security.md` and `security.de.md` about the security and privacy of the website, `about.md` and `about.de.md` about who builds the projects and how, which link the decision records, and `dashboard/index.html`, which forwards to the dashboard. The menu has three tabs: *Home*, with the Releases page, *Trust*, with the guarantees of the projects and the security page, and *About*, with the page of the same name and the automation of this repository. MkDocs with the Material theme builds them, and the Docs workflow publishes the website on GitHub Pages with every change of `main`. Preview it while you write, at <http://127.0.0.1:8000>, with the tools of the Docs workflow in a virtual environment of their own, `.venv-docs`, which git ignores:

```sh
python3 -m venv .venv-docs
.venv-docs/bin/pip install --require-hashes -r .github/docs-requirements.txt
.venv-docs/bin/mkdocs serve
```

On Windows, in PowerShell:

```powershell
py -3 -m venv .venv-docs
.venv-docs\Scripts\pip install --require-hashes -r .github/docs-requirements.txt
.venv-docs\Scripts\mkdocs serve
```

These are the commands of [CONTRIBUTING.md](CONTRIBUTING.md#website) and of the head of [mkdocs.yml](mkdocs.yml), and the scripts of [Pictures and icons](#pictures-and-icons) take their tools from the same `.venv-docs`.

The repository comes from the [blueprint](https://github.com/Dennis-Otto/repo-blueprint), whose bot keeps it current.

### The home page

Both home pages name [overrides/home.html](overrides/home.html) as their template. It shows the hero, on the navy of the social previews of the projects: the monogram, the name, a lead sentence and two buttons, *See the projects* and *Sponsor*. The texts of the hero come from the front matter of each page, under `hero:`, so that every language has its own. A landing page has no pencil that edits it, no date of its last change, no menu at its side and no footer that leads to the next page.

Below the hero, the projects stand in groups by their readers, each under a heading of its own: *For the smart home and the document archive* and *For maintainers on GitHub*. Each card has a picture of the project in the language of the page, its name, which links its website, a summary, a line that says what it works with, such as *Works with Home Assistant 2026.8.0 or newer*, and two buttons below it, both on one line on a phone: where to start, such as *Install with HACS*, and its documentation. The card of the blueprint leads to the dashboard instead, since its name links the documentation already. A sentence under the Paperless cards explains how the two apps work together. Every card of a project shows its [live facts](#live-facts), its latest release and the numbers of its quality, and *What's new* below the groups lists the latest release of every project, the newest first, each with the headline of its notes, and leads to the [Releases page](#the-releases-page). The pictures of the first group, which a reader sees as the page opens, load at once, the first before every other picture of the page, since it is the largest thing the page paints; those further down load as they come into view. Until a picture is there, its place has its size and the navy of the pictures, so no white box flashes in either color scheme. The page loads no diagram: the script of Mermaid would weigh about 1 MB on the most visited page.

On a phone, the hero fills the first screen: the menu folds into the button at the top left, the buttons of the color scheme, the language and the search stay in the header, and the buttons of the hero stand one below the other.

### One list of the projects

Every project is written once, in [projects.toml](projects.toml): its group, its name, its texts, its picture and its links, in English and German. While MkDocs builds the website, the hooks in [.github/mkdocs_project.py](.github/mkdocs_project.py) put the groups with a card for each project in place of the line `<!-- projects -->` of both home pages, in the language of the page. The same file writes the table of the projects above, between its two markers, and the German one of [README.de.md](README.de.md), with the German texts and the German addresses first:

```sh
python3 -I .github/mkdocs_project.py --write
```

A project without a group, such as the dashboard, has no card of its own: another card names it as its `second` button, and the check fails for a project that no card shows. The same list makes the 404 page, the sitemaps of robots.txt, llms.txt and the structured data of the home page, which [One address, every website](#one-address-every-website) describes, so a new project appears there without another edit; [Add a project](#add-a-project) lists the few steps that remain, and [the catalog bot](#the-catalog-bot) opens an issue for a project with a website at the address that the file lacks. The table holds every address of projects.toml, the German ones too, so that the link check, which reads the Markdown files, checks the buttons of the cards as well. `bash scripts/check.sh` fails when the table differs from projects.toml or a project lacks a German text, and on a pull request a table that differs [fixes itself](#the-checks-of-this-website), and the strict build of the website fails when a page or a title of the menu has no German translation.

### The catalog bot

The projects change without this repository: a new one gets its website at `dennis-otto.github.io`, another one translates its documentation, a third is renamed or archived. So every Monday the Catalog workflow, [.github/workflows/catalog.yml](.github/workflows/catalog.yml), compares projects.toml with GitHub and with the websites of the projects, and finds:

- a public repository of the owner with its website in a folder of `dennis-otto.github.io` that has no project in projects.toml;
- a project whose repository was renamed, archived, made private or deleted, or names another website on GitHub;
- a German website that appeared, such as `…/paperless-sync/de/`, while the German home page still leads to the English one, and a German website of projects.toml that answers 404;
- a file from which a card reads what its project works with, such as `hacs.json`, that is gone from the default branch of its repository on `raw.githubusercontent.com`, or that holds no version in its field any more, before the next release takes the line off the card;
- a screenshot or a logo from which the hub draws the German picture of a card, as `drawing` in projects.toml names it, that is gone from the default branch of its repository, before the next run of [the screenshot bot](#the-pictures-renew-themselves) stops at it;
- a color of the light behind that screenshot, `drawing.accent`, that the social preview of the repository lacks, its source `.github/social-preview.html` on the default branch, so that the German picture glows in another color than the English one, which is that preview; the issue names the `--accent` of the preview where it has one, and the bot sets that one itself, as below.

What the published website depends on after its build, the bot watches every day, as [the watch of the live websites](#the-watch-of-the-live-websites) describes.

It keeps one issue, *The project catalog is out of date*, with what it found and how to fix it, and closes the issue once a run finds projects.toml current. It needs no AI. A run started by hand from another branch than `main`, such as `gh workflow run catalog.yml --ref <branch>` to try a change of the bot, writes what it found into the summary of its run alone: the issue and the pull request say what `main` needs, so it changes neither, and the watch does the same with its own issue.

A difference with one correct edit needs no person to write it, only one to merge it. The bot makes these edits itself, after it asked the web for each address and read the social preview of each repository:

- a German website that appeared: `docs.en` and `docs.de` in place of `docs`;
- a German website that is gone, beside an English one that answers: one `docs` in place of `docs.en` and `docs.de`;
- a website that its repository names in another folder of the address, which answers, where the folder of the catalog is gone: the new address in every language. Such a move also needs `former` for the readers who still come to the old folder, and the tests that name the folder, which a person pushes onto the branch of the pull request.
- a drawn picture whose light, `drawing.accent`, is a color that the social preview of its repository lacks, where the preview names one `--accent`, the same wherever it names it: that accent. The light changes no other file, and the merge brings the new picture: projects.toml is among the files whose change on `main` starts [the screenshot bot](#the-pictures-renew-themselves), which draws the German picture anew in its own pull request.

The edit changes only the lines of the address or the line of the light, inside the `[[project]]` of its slug, with every comment and the order of the file as they were, and it is made only if the file reads back as the wanted catalog. After an address, the tables of the READMEs, the links of the pages of the website and the data of the tests of the script of the not-found page follow, so that the checks of the pull request pass. The bot keeps one pull request from the branch `bot/catalog` with them, marks those differences in the issue and names the pull request there; it closes the pull request when `main` needs no edit any more, and leaves one with a commit of a person alone. Everything else stays in the issue for a person: a repository that was renamed, archived, made private or is new, a file that a card or a picture needs, a second website that answers beside the one of the catalog, a website that is away altogether, and a light whose social preview names no `--accent` of its own or two different ones, so that only a person can choose among its colors.

The comparison may only read the repository and write issues, holds no secret, and commits nothing. Only the job that follows it, *catalog pull request*, has the release app, so that the checks of the pull request run: it asks the app for what a branch and a pull request need alone, checks out only its own script, [scripts/catalog-pull-request.sh](scripts/catalog-pull-request.sh), from the commit of `main` that the run compared, runs nothing that the comparison made, and commits only projects.toml, the READMEs, the pages of the website and that data. The tests in `tests/test_catalog_pull_request.py` run that script in bash against a fake gh, with the real jq, for each way it can go: a new pull request, an update of an open one, one with a commit of a person, one of a fork, a file outside what it commits, and no edits with or without an open pull request. Without the app, the issue still says each edit. Harden-Runner blocks every host but those of the steps of a job, `api.github.com`, `github.com`, `dennis-otto.github.io`, `raw.githubusercontent.com` and the store of the artifacts for the comparison, `api.github.com`, `github.com` and the store of the artifacts for the pull request (and `api.github.com` alone for the daily build), and the hosts of GitHub that the runner itself needs, and takes sudo and Docker away, so a compromised dependency or action can't send a token anywhere outside GitHub and `dennis-otto.github.io`. The comparison needs the standard library alone, so it runs locally too, with the list of the repositories that gh writes, and `--fix` makes the edits in your copy, with the text of their pull request in the file that it names:

```sh
gh repo list Dennis-Otto --limit 1000 --json nameWithOwner,homepageUrl,isArchived,isPrivate >repositories.json
python3 -I .github/mkdocs_project.py --network repositories.json
python3 -I .github/mkdocs_project.py --network repositories.json --fix pull-request.md
```

#### The watch of the live websites

The checks of a pull request and [the check of the built website](#the-check-of-the-built-website) test what a build writes. Once it is published, the website depends on things that change without this repository and that no build checks again: the data of the dashboard, which the blueprint publishes every two hours and from which the cards take their [live facts](#live-facts), the search indexes of the project websites, which the next build takes into [the search](#one-search-for-every-website), and the files that only the daily build keeps current. A change there degrades the website without a sign, by design: the cards keep the facts of the build, and a project website without its index drops out of the search. So every day at 06:17 UTC, after the daily build, the job *watch* of the Catalog workflow asks the live websites, and finds:

- `repos.json` or `history.json` of the dashboard that is gone or no JSON, has another `schema` than the one that the script knows, lacks a field that the script reads or holds a value of another kind, such as a score as a text, as [.github/dashboard-fields.json](.github/dashboard-fields.json) names them, a `repos.json` whose `generated`, the time at which the dashboard wrote it, is missing, no time with its zone or more than 24 hours old, though the dashboard writes it every two hours, so that a dashboard that stopped publishing without a failed run shows within a day instead of old releases and scores for days, and a project with a card that `repos.json` has no entry for;
- a project website whose search index answers 404, isn't one of Material for MkDocs or holds no entry, before the next build leaves the website out of the search;
- a project with a repository whose release notes the Releases page lacks, so that *What's new* leaves it out, and a project website that the search index of this website has no entry of: a build that can't read the API of GitHub or the index of a project website passes and says so only in its log, its summary and a warning of the run, so that a loss that lasts, such as of a token that no longer reaches the hooks, would otherwise go unseen; each line asks for a rebuild, after a look at the log;
- a copy of `security.txt` that is missing or holds for 330 days or fewer, though every build renews it to 365, so that a daily build that stopped shows within a month instead of after a year; `robots.txt` without the sitemap of a website of the address; and the sitemap of this website without the root of the address;
- an old address of `former/<folder>.txt` that answers 404 or doesn't lead to the same page in the new folder, and one whose page there answers 404, because its project moved or removed the page.

It keeps one issue, *The live websites need attention*, with the label `maintenance`, in which every line names the address, what readers lose and the fix, writes the same into the summary of its run, and closes the issue once a run finds nothing. An address that can't be reached is asked twice, and one that still can't be reached or answers oddly fails the run without touching the issue, as the catalog bot does. Harden-Runner lets the job reach `api.github.com`, `github.com` and `dennis-otto.github.io` alone, and takes sudo and Docker away. The watch needs the standard library alone, so it runs locally too, and `gh workflow run catalog.yml -f job=watch` starts it at once:

```sh
python3 -I .github/mkdocs_project.py --watch
```

### Add a project

A new project, such as one that the catalog bot reports, needs its entry in projects.toml and its pictures; the rest follows from them.

1. Add a `[[project]]` to [projects.toml](projects.toml), where its card belongs: its group, its texts in English and German, its picture and its links, what it works with in `requires`, best from the file of its repository that holds the versions, and for a project whose releases carry a package, its `asset`, which the commands of the Trust page check. The comments at the top of the file describe every key.
2. Make the pictures of its card, and write its `alt` texts as those of the other cards: with the name of the project and what every picture keeps, as [the pictures renew themselves](#the-pictures-renew-themselves) from then on. The English picture comes from the social preview of its repository; for the German one, give it `image.de` and a `drawing` with a screenshot of its repository, in German where it has one, its logo and the color of its social preview, and `drawing.hangs = true` for a screenshot that is cut at its foot already, such as a popup below the toolbar of a browser, and the script draws it:

   ```sh
   bash scripts/project-pictures.sh
   ```

3. Write the table of [the projects](#the-projects) anew, with `py -3` in place of `python3` on Windows; a pull request from a branch of this repository without it gets the table from [the fix bot](#the-checks-of-this-website), one from a fork does not:

   ```sh
   python3 -I .github/mkdocs_project.py --write
   ```

4. ### Rename a project

GitHub Pages publishes the website of a renamed repository in the folder of its new name and leaves nothing in the old one, whose addresses then reach this website, as every address does that no project serves. So this website keeps them working, as [decision 0004](docs/decisions/0004-the-root-website-keeps-the-old-addresses-of-a-renamed-project.md) records:

1. Change the entry of the project in [projects.toml](projects.toml): its `slug`, `repo`, `start` and `docs`, and its texts, its `asset` and its picture where they change, as in [Add a project](#add-a-project).
2. Name the old folder of its website in `former`, such as `former = ["ha-autodarts"]` for HomeDarts for Autodarts, and list the pages of the old website in `former/<folder>.txt`, from its sitemap, before the repository is renamed. With the name of the old folder in `folder`:

   ```sh
   folder=ha-autodarts
   curl -fsS "https://dennis-otto.github.io/$folder/sitemap.xml" |
     grep -oE "https://dennis-otto\.github\.io/$folder/[^<\"]*" |
     sed -e "s#^https://dennis-otto.github.io/$folder/##" -e 's#^$#index.html#' -e 's#/$#/index.html#' |
     sort -u
   ```

3. Write the table of [the projects](#the-projects) anew, name the project by its new name in the lists of step 4 of [Add a project](#add-a-project), and run the checks.

While MkDocs builds the website, the hooks write a page at every old address of the list, such as `/ha-autodarts/de/games.html`, which leads to the same page in the new folder at once, with the query and the fragment of the address, such as `#cricket`; without JavaScript, its refresh and its link lead there. It names the new address as its canonical one and asks search engines to list no page of its own. The 404 page leads every other address of the old folder, such as that of a picture or of a page that the old website added after its list, to the same path in the new folder, and the card of the project keeps the anchor of the old folder, such as `/#ha-autodarts`. `bash scripts/check.sh` and the build fail for a folder of `former` that the address or the home page uses already, as a language, the folder of a website, a slug or the id of a group, and for a list of old pages that is missing or holds a line that is no path of a page; the strict build fails when this website puts a file of its own into such a folder.

The pages wait behind the website of the project until its repository is renamed, since GitHub Pages serves a folder of a project before this website, so the change can come before the rename. Never give a new repository an old name: its website would hide the pages again, and GitHub would stop sending the address of the old repository to the renamed one.

After MkDocs has built the website, the hooks in [.github/hub/search.py](.github/hub/search.py) download the search index of every project of projects.toml whose documentation lies in a folder of the address, such as `/homedarts-for-autodarts/search/search_index.json`, and add its pages and sections to `/search/search_index.json`, the one index of both languages of this website:

- Every location moves into the folder of its project, so that a result opens the page on the website of the project, in its language.
- Every title of a page starts with the short name of its project and `›`, such as *HomeDarts › Games and rules*: `short` in projects.toml, or its `name`. The sections stand under their page, as on the website of the project.
- Every text becomes an excerpt: plain text without its tags and its blocks of code, such as the source of a diagram, cut after a whole word at 200 characters at most and escaped, so that an index can carry no markup into this website.
- Every entry gets a rank from the name of its page, in every language, such as `installation.html` and `de/installation.html`. First comes the entry of every page, with its title and its text before the first heading; then the sections of the pages that a reader looks for first, `getting-started`, `install`, `installation`, `setup`, `guide`, `help`, `how-it-works`, `shared-display`, `faq` and `troubleshooting`, such as the help and the shared display of Player Switch and the setup and how it works of Repo Pager; then the sections of those pages in a further language of their website, such as `de/faq.html` or `nl/faq.html`, so that a FAQ in five languages never pushes the help of a smaller website out; then those of the other pages; and last those of the pages for maintainers, `changelog`, `releases`, `development`, `automation` and `roadmap`. A decision record, a page in a folder named `decisions`, keeps the entry of its page and none of its sections.
- The projects add 120,000 bytes at most, packed with gzip as GitHub Pages sends the index. The budget gives up the entries of the last rank first, and the entries of the pages last: of the sections of a rank, the page with the most gives up its last ones first, such as the oldest releases of a changelog, and of the pages, the largest website gives up its last ones first. So the search finds every page of every project in both languages: in November 2026 the projects added all of their 544 pages and 1,098 of their sections, 114 KB, among them every section of the help of Player Switch and of the setup of Repo Pager, and left out the sections of the decision records and of the pages for maintainers. The log of every build says how many pages and sections of each website the search keeps, so that a drop shows there.
- The search of Material for MkDocs ranks the matches of an entry by its `boost`: the pages that a reader looks for first and their sections count twice, those for maintainers and the decision records half, also the decision records of this website, so that *installation* finds the installation of HomeDarts before a decision record that mentions it. A project website's own boosts stay on that website.
- Every page asks for the index only when the reader goes to the search box, or a second after the page has loaded, when the browser is idle: [overrides/partials/search-hold.js](overrides/partials/search-hold.js), which [overrides/main.html](overrides/main.html) puts into every page, holds back the request of Material for MkDocs, which would otherwise share a slow connection with the fonts and the pictures of the first paint. With it, Lighthouse rates the home page on a phone 0.95 to 0.98, as without the projects in the search.

A download may take 10 seconds and is tried twice, 2 seconds apart, or as long as the answer asks, as the API of GitHub does with `Retry-After` or the moment at which its limit of requests resets, when that is 30 seconds away at most; for a longer wait the build goes on without the file at once, and all downloads of a build wait 2 minutes together at most, well within the 5 minutes of the step. A project website that can't be downloaded, or whose index isn't one, stays out of the search until the next build, and the log of the build says why without a warning, so the strict build passes while a project website is away. The summary of the run of the Docs workflow shows the same as a table, with a row for each project website: how many of its pages and sections the search keeps, or why it left the website out. And [the watch of the live websites](#the-watch-of-the-live-websites) asks every project website for its index every day, so that one whose index stays away gets an issue. Every day at 04:41 UTC the Catalog workflow starts the Docs workflow on `main`, which builds and publishes the website again, so the search follows the documentation of the projects within a day. To build it at once, run `gh workflow run catalog.yml -f job=rebuild`.

### Live facts

Every card of a project shows what sets the project apart, as numbers that a reader can check: its latest release and how long ago it came out, the share of its code that its tests run, the share of mutants of its code that they catch, the score of its repository in the [OpenSSF Scorecard](https://scorecard.dev/), the median time to the first answer by a person to a new issue, and the level that it holds in the [OpenSSF Best Practices](https://www.bestpractices.dev/). *What's new*, below the groups, lists the latest release of every project, the newest first, each with the headline of its notes, such as *HomeDarts for Autodarts v2.0.1 · 3 days ago* and *Ask Assist about your darts sounds more natural in German, Spanish, French and Dutch*, linked to its notes on the [Releases page](#the-releases-page). In German, the texts and the numbers are German too, such as *vor 3 Tagen* and *100 % Testabdeckung*.

- **The release and the numbers come from the dashboard.** Every two hours the [dashboard of the blueprint](https://dennis-otto.github.io/repo-blueprint/dashboard/) publishes its data beside itself, at the same address as this website: `repos.json`, with the latest release and the numbers of every repository, `history.json`, with the numbers of every day, and `releases.atom`, the feed of the releases of all projects. As a home page loads, [docs/javascripts/projects.js](docs/javascripts/projects.js) reads `repos.json`, or the numbers of the latest day of `history.json` when it can't, and writes them into the cards in the language of the page. So the numbers stay current without a new build of the website, and the page asks no other server, needs no token and meets no limit of an API. The script reads only the shape of `repos.json` that it knows, its `schema` 1, writes every text with `textContent`, and links only addresses on GitHub.
- **The level of the OpenSSF Best Practices comes from the build.** The hooks in [.github/hub/render.py](.github/hub/render.py) read it from bestpractices.dev for every project that names its number there, `bestpractices` in projects.toml, and write it into its card, linked to its page; the Catalog workflow builds the website every day. The website shows no badge: the privacy plugin would keep it as the build downloaded it, so the hooks of the blueprint take every badge out of a page. A level that can't be read stays off the card until the next build, which passes.
- **What's new comes from the build, and the script keeps it current.** The hooks write the latest release of every project with the headline of its notes, without the scope of a commit in front, such as `deps:`, from the releases that they read for the [Releases page](#the-releases-page), as many as projects.toml has projects with a repository. A release of maintenance alone says so, *Maintenance release* or *Wartungsrelease* as `maintenance` of `[facts]` in projects.toml has it, rather than read like a changelog for the maintainer: every pull request that its notes list has the scope `ci`, `build`, `test`, `refactor`, `style` or `chore`, or `deps` or `docs` while no line of the notes says in the words of a user what that changes. As the page loads, the script puts a newer release of `repos.json` in the place of one that came out after the build, linked to its notes on GitHub, and tells the day of every release as the time since, such as *3 days ago*.
- **Without the data or without the script,** every card keeps what the build wrote into it, and *What's new* the releases of the build, each with its day as a date, and its sentence, which links the Releases page, the dashboard and the feed. The head of the home pages names no feed: Material asks the folder of every alternate link there for a `sitemap.xml`, which the dashboard doesn't publish, so the link would cost every reader a failed request.
- **The shape of the data is watched.** Since the cards keep the facts of the build when the data changes its shape, nobody would see that the live facts are gone. [.github/dashboard-fields.json](.github/dashboard-fields.json) names what the script reads: the `schema` of `repos.json` that it knows, and the kind of every field of an entry, of its `health` and of a day of `history.json`, such as `released`, a day or null, and in `feed` the fields of `repos.json` itself that the script does without and the watch alone reads, `generated`, a time. The tests of the script fail when it reads a field that the file doesn't name or knows another schema, and [the watch of the live websites](#the-watch-of-the-live-websites) checks the live data against the file every day.

### The Releases page

[The Releases page](https://dennis-otto.github.io/releases.html), *Neuigkeiten* in German, shows what changed in every project: the notes of its latest five releases, the newest first, under a heading of each project, in the words of its users, as its changelog has them. A row of links at the top and the table of contents lead to each project, also without JavaScript; the search finds the notes; and the page links the feed of all releases for a feed reader, and below the releases of each project, beside the link to all of them on GitHub, the feed of that project alone, `https://github.com/<repo>/releases.atom`. The hooks write it in place of the line `<!-- release-notes -->` of `docs/releases.md` and `docs/releases.de.md`:

- **The notes come from the API of GitHub at the build.** For every project with a repository, the hooks ask `api.github.com/repos/<repo>/releases` once a build, for both languages, for the HTML that GitHub makes of the Markdown of the notes, and leave out drafts and prereleases, such as the betas for testers. The Catalog workflow builds the website every day. A release that came out since, the script adds as the page loads, from `repos.json` of the dashboard, under the heading of its project, with a link to its notes on GitHub. A token in `GITHUB_TOKEN` or `GH_TOKEN`, where one is set, lifts the limit of the API from 60 requests an hour to 5,000; the hooks send it to the API alone, never to a host that the API leads on to.
- **No HTML of a release reaches the page as it is.** Of the notes, the page keeps text, paragraphs, lists, headings, tables, code, quotes and links to `https://` addresses, without an attribute but the address of a link: no script, no style, no picture, no frame and no form. The notes take the place of their placeholder in the HTML of the page, after Markdown, so no extension of Markdown reads them, such as the snippets that include a file. Their headings stand below the heading of their release, a heading in front that names the version is left out, and a line break that GitHub makes of every line of their Markdown becomes a space.
- **The notes for users, once.** Below the notes for users, the release bot of the blueprint lists every pull request of the release under the heading *Every pull request of this release*: the same changes again, as the subjects of their commits. The page leaves that list to the link of each release on GitHub, so a reader, a screen reader and the search meet each change once. Notes with nothing above that heading keep the list, and *What's new* still reads it, to tell a release of maintenance by the scopes of its pull requests.
- **Dated by its releases.** The sitemap and the date of the last change of a page take the last commit of its Markdown, while the Releases pages and the home pages, with *What's new*, change with every release of a project. The hooks date these pages by the newest release that the build read, when it came out later, so a search engine reads from the sitemap that they changed, and the Releases page shows that date as its last change; `--site` fails the check when the sitemap dates a page before the newest release that it shows.
- **Without the API,** as on a computer without a network or when its limit is reached, the build passes, and the page keeps the heading of every project with a link to its releases on GitHub; *What's new* leaves its place to the script, as before, and the card has no *Works with* until the next build. - **The notes stay in English,** the language of the changelogs, also on the German page, which names their language for screen readers. Each language has a search index of its own, so the German index holds the English notes once, from the German page, and the search finds them in both languages.
- **The texts** of the page, the name of the row of links, the link of each release to GitHub and the link to all releases of a project, are in `[facts]` of projects.toml, in English and German.

## Development

Every change goes through a pull request whose title follows [Conventional Commits](https://www.conventionalcommits.org/), with signed-off commits (`git commit -s`). The checks of the CI run locally with

```sh
bash scripts/check.sh
```

[CONTRIBUTING.md](CONTRIBUTING.md) explains the set-up and the rules.

### Coding standards

The code of this website follows the standards of the blueprint for its languages, beside those that [CONTRIBUTING.md](CONTRIBUTING.md#coding-standards) names for the shell scripts, the workflows, the Markdown and every text file:

- **Python**, the hooks in `.github/mkdocs_project.py` and `.github/hub/`, `scripts/screenshots.py` and the tests, follows [PEP 8](https://peps.python.org/pep-0008/) in the format of [Ruff](https://docs.astral.sh/ruff/), which matches Black, with the rules of Ruff that [ruff.toml](ruff.toml) selects, those of the blueprint: pycodestyle, Pyflakes, isort, flake8-bugbear, pyupgrade, flake8-simplify, flake8-pytest-style and the rules of Ruff itself. The code has type hints, which mypy checks in its strict mode with [mypy.ini](mypy.ini), and runs on Python 3.11 or newer.
- **JavaScript**, the scripts that the browser runs from `docs/javascripts/` and `overrides/partials/` and their tests in `tests/`, follows the format and the recommended rules of [Biome](https://biomejs.dev/), with sorted imports and the indentation of `.editorconfig`, as [biome.jsonc](biome.jsonc) sets them up, the settings of the JavaScript projects of the blueprint. The scripts are classic scripts in strict mode, without a step that builds them.

`bash scripts/check-project.sh` checks both, as [the checks of this website](#the-checks-of-this-website) say, with the tools of `requirements-test.txt` and `tests/lint/package-lock.json`, and `bash scripts/check-project.sh --fix` fixes what Ruff and Biome can. The code of the blueprint in `.github/`, such as `.github/blueprint/`, keeps the settings of the blueprint, which checks it there. An exception to a rule is rare and has its reason in a comment at its place, as in `ruff.toml` and `biome.jsonc`.

### The tests of the scripts

The website runs three scripts of its own in the browser of a visitor. Each is a file with its tests in `tests/`, which run it as the browser does, in a context of its own with a page, an address and the requests of the browser made for the test, so they need Node.js 22.8 or newer and no package:

| Script | What it does in the browser | Its tests |
| --- | --- | --- |
| [docs/javascripts/projects.js](docs/javascripts/projects.js) | Writes the [live facts](#live-facts) into the home pages, the Trust page and the Releases page; [overrides/facts.html](overrides/facts.html) loads it there. | [tests/projects.test.mjs](tests/projects.test.mjs) |
| [overrides/partials/not-found.js](overrides/partials/not-found.js) | Leads an address in the old folder of a renamed project to the same path in its new folder, with its query and its fragment, and suggests a project for every other address that leads nowhere. [overrides/404.html](overrides/404.html) puts it inline into the 404 page, with its data as JSON, `#not-found-data`, from projects.toml. It leads to and links only the addresses of its data at https, each written anew from its encoded parts, so that broken data can't lead a reader to a `javascript:` address. | [tests/not-found.test.mjs](tests/not-found.test.mjs) |
| [overrides/partials/search-hold.js](overrides/partials/search-hold.js) | Holds back the [search index](#one-search-for-every-website) until the reader goes to the search box, or until the browser is idle after the page has loaded. [overrides/main.html](overrides/main.html) puts it inline into every page, before the scripts of the theme. | [tests/search-hold.test.mjs](tests/search-hold.test.mjs) |

The two scripts of `overrides/partials/` are inline, so that a page asks for no further file, and Jinja reads them as part of the template: their tests check that neither holds `{{`, `{%`, `{#` or the end tag of a script, and that the templates include them and nothing else. `mkdocs.yml` leaves them out of the website as files of their own. Run the tests as `bash scripts/check-project.sh` does:

```sh
node --test --experimental-test-coverage \
  --test-coverage-include='docs/javascripts/*.js' --test-coverage-include='overrides/partials/*.js' \
  --test-coverage-lines=100 --test-coverage-branches=100 --test-coverage-functions=100 \
  tests/*.test.mjs
```

The step fails when the tests leave a line, a branch or a function of a script out, and names its lines. Node measures only the scripts that a test loads, so [tests/scripts.test.mjs](tests/scripts.test.mjs) also fails for a script without its own `tests/<name>.test.mjs`; the coverage table at its end shows each script. The CI logs the version of Node it runs them with, and fails without Node 22.8 or newer; a computer without it leaves the tests to the CI and says so.

The twelve runs, six scenarios at two widths, take a few seconds together, each in a browser of its own. They read nothing from the network: every request to the address gets the answer of GitHub Pages, a file of `site` or its 404 page with the status 404, the data of the dashboard at `/repo-blueprint/dashboard/repos.json` comes from [tests/fixtures/repos.json](tests/fixtures/repos.json), which the tests of `projects.js` read too, a page of a project website is a stand-in, and a request to another server is refused, and the log names its server. A scenario that fails names its title, the width and what broke, with the file that does it, in the log, as an annotation and in the summary of the check, and keeps a screenshot and a trace of Playwright in `site/.e2e/`, such as `search-phone.png` and `search-phone.zip`. The artifact *website* of a pull request holds them (a push to `main` uploads no artifact, so a failure there is reproduced with the commands below), and [trace.playwright.dev](https://trace.playwright.dev) opens a trace in the browser, without sending it anywhere, with every step and the page as it looked; the PR coach explains the check in the words of [.github/checks.project.toml](.github/checks.project.toml), with every scenario by its title, which [tests/test_checks_project.py](tests/test_checks_project.py) keeps in step with the script.

`scripts/check-site.sh` runs them after the build above with Node.js 20 or newer and Google Chrome; `CHROME=/path/to/chrome` names another Chrome or Chromium. It installs `playwright-core` from [tests/e2e/package-lock.json](tests/e2e/package-lock.json), which Renovate keeps current, and again when the lock file changes. Without Node or Chrome, it says so and leaves the scenarios to the CI, where a missing one fails the check. To run the scenarios alone, after a build:

```sh
npm ci --prefix tests/e2e --ignore-scripts
node tests/e2e/hub.mjs site
```

## Support and security

A question, a problem or an idea about a project belongs to the issues of its own repository, which the table above links. The [issue chooser](https://github.com/Dennis-Otto/dennis-otto.github.io/issues/new/choose) of this repository links each project's issues too; its own two forms are for the website itself, a problem with a page or an idea for it. The documentation of a project, under `dennis-otto.github.io/<project>/`, is built by the project's repository, and its issues take reports about it. [SUPPORT.md](SUPPORT.md) says what happens with an issue. Report vulnerabilities privately, as [SECURITY.md](SECURITY.md) describes; the [security page](https://dennis-otto.github.io/security.html) links the private report form of every website of the address, and says what the website keeps in the browser, which servers a page asks and which risks remain.
